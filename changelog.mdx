<Update
  label="November 6, 2026 - Fixes"
  tags={["Fixes", "API"]}
  rss={{
    title: "Spot bad quote IDs sooner and keep sandbox polling working",
    description: "Session creation now flags a malformed quote_id with a 400 validation error instead of a misleading 404. Sandbox payment-result polling returns the order status instead of a 500 when a simulated order was never paid."
  }}
>
  ## Spot bad quote IDs sooner and keep sandbox polling working

  - **Find the real problem straight away:** when `purchase_context.quote_id` is malformed,
    `POST /v1/sessions` now returns a `400` validation error pointing at that field. A broken
    value, such as `"None"` left over from a failed quote request, no longer looks like a
    missing quote (`404 QUOTE_NOT_FOUND`). Send the `qte_…` ID exactly as quote creation returned it.
  - **Sandbox polling keeps working:** `GET /v1/sessions/{sessionId}/payment-result` now
    returns `200` with the order's status when a sandbox session requested success simulation
    but never paid, for example because another session paid the same quote. Previously this
    failed with `500`. A declined payment is still never reported as completed.

  [Create a session →](/api-reference/create-session) · [Sandbox simulation →](/api-reference/testing#simulate-successful-payment-completion)
</Update>

>
  ## Know when a card added at checkout is fully set up

  When a shopper adds a new card during checkout, you now receive `card_enrollment.completed`
  once the card and its passkey are fully set up, whether or not the payment succeeds. The event
  includes the new card's `card_id` and the original checkout `session_id`. Paying with a card
  that's already saved doesn't send it.

  For cards added at checkout, the event's resource ID starts with `sa_` instead of the `ses_`
  you get from standalone card enrollment. Use `data.card_id` and `data.session_id` to match the
  event to your records.

</Update>

<Update
  label="October 29, 2026 - Card lifecycle webhooks"
  tags={["New", "API", "Webhooks"]}

  }}
>
  ## Keep saved cards in sync with card webhooks

  Applications can subscribe to `card.saved` when a new card is durably stored
  and `card.deleted` when it is deleted. Events identify the card and
  Prava customer and your original `user_id`, with an owned session when available. Existing subscriptions
  remain unchanged; earlier card saves are not backfilled.

  Save and delete use card resource versions `1` and `2`. Deduplicate by event ID
  and retain the newest card version when deliveries arrive out of order.
  These events are separate from payment success and full-enrollment results.

  New regular and quote-backed mandate charges also identify the original
  setup card in payment events when it can be determined safely.
  Otherwise the Card ID remains null; earlier records are
  not backfilled.

  When a shopper chooses to add a new card, the card form now opens right away instead of

<Update
  label="October 24, 2026 - Webhooks"
  tags={["New", "API", "Dashboard", "Webhooks"]}
  rss={{
    title: "Prava webhooks are live: stay in sync with payments and mandates",
    description: "Applications with webhooks enabled can subscribe to signed payment-attempt, card-enrollment, and mandate events. Configure and test endpoints in the dashboard, inspect delivery failures, and recover retained events."
  }}
>
  ## Prava webhooks are live: stay in sync with payments and mandates

  Receive signed updates when payment attempts, card enrollment, or mandates change, so your
  application can react without polling every session.

  - **Follow outcomes:** Subscribe to payment, card-setup, and mandate events, including
    mandate pause, resume, cancellation, and expiry. Failure events include stable, buyer-safe
    codes and distinguish a failed payment from a definite credential-issuance failure.
  - **Set up your receiver:** Choose events in the dashboard or API, save the signing secret,
    verify the destination, send a test event, and activate delivery.
  - **Recover delivery:** Inspect delivery history and endpoint health. If a receiver keeps
    failing, Prava pauses it; fix the receiver, resume delivery, and replay retained events.

  A payment event describes the payment attempt, not final merchant order fulfillment.
  Subscriptions, signing secrets, and event history are separate for sandbox and production.
  Webhooks must be enabled for the selected environment.

  [Set up webhooks →](/webhooks/overview) · [Review events and delivery →](/webhooks/events)
</Update>

  ## More reliable checkout completion and payment reporting

  Payment completion now uses the persisted transaction amount as its source of truth and
  applies lifecycle changes atomically. Duplicate completion calls, concurrent callbacks, and
  repeated result polling return the authoritative state without decrementing limits, consuming
  a mandate, or completing an order more than once.

  bounded three-attempt delivery budget with shorter per-attempt timeouts, so an uncertain
  confirmation cannot retry indefinitely or overwrite the saved payment outcome.

    still pending.

    the saved payment outcome remains authoritative while confirmation is reconciled.

<Update
  label="July 19, 2026 — Mandates"
  tags={["New", "API"]}
  rss={{
    title: "Manage standing mandates and reconcile each charge",
    description: "Set up mandates through sessions, filter by customer, inspect charge history, and pause, resume, or cancel future charging. One-time standing mandates are capped at seven days."
  }}
>
  <span id="september-2026-mandates" />

  ## Manage standing mandates and reconcile each charge

  Add `mandate_setup` with `intent: "mandate_setup"` to a session to collect approval
  for future charges. After activation, charge the mandate without another passkey prompt.
  One-time standing mandates are capped at seven days; a later `valid_until` does not extend
  that window. Check `validUntil` before scheduling a charge.

  - **Find the right mandate:** `GET /v1/mandates` accepts `customer_id` for merchant callers,
    using either their external customer ID or a Prava customer ID. Responses include `approvedAmount`, `remaining`,
    `validUntil`, `renewsAt`, and `lastCharge`; the detail endpoint includes charge history.
    Displayed balances are derived from recorded activity; Visa enforces the spending limit.
  - **Track each charge:** `POST /v1/mandates/{id}/charge` creates its own order and transaction.
    Send a decimal-string `amount` and an optional `reference` to deduplicate retries within
    that mandate. Failed charges release the reference for retry. Currency comes from the
    mandate; an optional per-charge `purchase_context` remains a one-entry array.
  - **Report the outcome:** Send `txn_status: "APPROVED"` or `"DECLINED"` to
    `POST /v1/mandates/{id}/charges/{txnId}/report` to reconcile the charge and report to Visa.
    `txn_type` defaults to `"PURCHASE"`.
  - **Control future charging:** `POST /v1/mandates/{id}/pause`, `/resume`, and `/cancel`
    manage the mandate's Prava state. Cancellation is terminal in Prava; these controls
    do not revoke the underlying Visa instruction.

  Charging and reporting require a merchant secret key or a direct agent signature.
  Charge requests are not exposed through MCP.
